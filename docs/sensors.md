# Источники показателей

Источники текущей реализации и направления расширения. Kernel-модуль датчиков
разрешён пользователем; подписанный пакет PawnIO встроен как опциональный компонент.
Проверки на конкретных машинах ведутся отдельно в [матрице железа](hardware-matrix.md):
исходный код и CI не являются подтверждением показаний на плате.

## Кадры: ETW вместо инъекций

| Проект | Лицензия | Как получает кадры | Почему не берём целиком |
|---|---|---|---|
| [GameTechDev/PresentMon](https://github.com/GameTechDev/PresentMon) | MIT | ETW-сессия реального времени, провайдеры DXGI, D3D9, DxgKrnl, DWM | Зависимость на 100k строк, служба и собственная модель данных; нам нужен только потребитель Present-событий |
| RTSS / MSI Afterburner | закрытый код | хуки в `Present` внутри процесса игры | Требует инъекции DLL: античиты и антивирусы реагируют, для портативного монитора это неприемлемый риск |
| fps_inspector_sdk | без явной лицензии | ETW | Лицензия не позволяет встраивание |

Взято из PresentMon: GUID и идентификаторы событий (сверены с `PresentData/ETW/*.h`),
настройки сессии (буфер 64 КБ, 256…1024 буфера, `EVENT_TRACE_REAL_TIME_MODE`, метка времени
QPC). Код потребителя написан свой, без зависимости.

Используемые провайдеры:

| Провайдер | GUID | Событие | ID |
|---|---|---|---|
| Microsoft-Windows-DXGI | `CA11C036-0102-4A2D-A6AD-F03CFED5D3C9` | `Present_Start` | 0x2A |
| Microsoft-Windows-D3D9 | `783ACA0A-790E-4D7F-8451-AA850511C6B9` | `Present_Start` | 0x0001 |

Кадром считается `Present_Start`: `Present_Stop` закрывает тот же кадр, и учёт обоих
событий удваивал бы FPS. Ключ провайдеров — `0x8000000000000002` (Analytic + Events).
Вызовы с флагом `DXGI_PRESENT_TEST` (проверка окна без кадра) отбрасываются.

### Чей FPS показывать: как в RTSS

Кадры в сессию приходят от всех процессов сразу. Раньше «игрой» считался самый быстрый
поток, и на мониторе 144 Гц композитор рабочего стола (`dwm.exe`) обгонял игру со 120
кадрами — программа показывала 144. Теперь порядок такой:

1. процесса активного окна (`GetForegroundWindow` → pid), если он не служебный;
2. иначе самый быстрый поток, но служебные процессы (`dwm.exe`, `explorer.exe`, хосты
   оболочки, `csrss.exe` и т.п.) вперёд не выдвигаются никогда.

Цифра FPS считается по последней секунде (сумма интервалов кадров за окно 1000 мс), как в
RTSS, а не по одному последнему кадру: иначе значение дрожит и расходится с тем, что видит
игрок. Если вся сессия не получает новых Present-событий более двух секунд,
история кадров сбрасывается и старый FPS не выдаётся за текущий; при возобновлении
кадры набираются заново. Если другие процессы продолжают отдавать кадры, трекер
отбрасывает остановившийся поток относительно времени их последнего события.

Ограничение: Vulkan- и OpenGL-игры презентуют через DWM, их кадры в этих событиях не видны —
для них остаётся оценка по композитору (этап 5).

## Загрузка и память GPU

- **DXGI** (`IDXGIFactory1`, `IDXGIAdapter1::GetDesc1`) — имена, LUID и физический
  `DedicatedVideoMemory`. `QueryVideoMemoryInfo` возвращает бюджет процесса, **не** общий
  объём и **не** суммарную занятость карты. Права администратора не нужны.
- **PDH** `\GPU Adapter Memory(*)\Dedicated Usage` по LUID — общая занятость выделенной
  памяти адаптера. Если счётчик недоступен, значение остаётся неизвестным, не 0,1 ГБ.
  Для NVIDIA при доступности используем `nvmlDeviceGetMemoryInfo` драйвера
  (used/total по выбранной карте); PDH остаётся резервом.
- **PDH** `\GPU Engine(*)\Utilization Percentage` — тот же источник, что у диспетчера задач;
  инстансы содержат LUID адаптера, поэтому два GPU не смешиваются.

## Медиа-движки, PCI-e и файл подкачки

| Датчик | Источник | На чём работает |
|---|---|---|
| Кодирование видео | PDH `\GPU Engine(*)\Utilization Percentage`, инстанс `engtype_VideoEncode` по LUID | NVIDIA, AMD, Intel — движок общий для всех трёх |
| Декодирование видео | тот же счётчик, `engtype_VideoDecode` | NVIDIA, AMD, Intel |
| Кодирование/декодирование (уточнение) | NVML `nvmlDeviceGetEncoderUtilization` / `GetDecoderUtilization` | только NVIDIA; берётся максимум с PDH-значением |
| Нагрузка PCI-e | NVML `nvmlDeviceGetPcieThroughput` (TX+RX) к теоретической пропускной способности линии (`GetCurrPcieLinkWidth` × `GetCurrPcieLinkGeneration`) | только NVIDIA; на AMD и Intel честно «нет данных» |
| Загрузка ОЗУ | `GlobalMemoryStatusEx`: занято / всего, % | везде |
| Загрузка файла подкачки | занято / (commit limit − физическая память), % | везде |
| Объём файла подкачки | `GetPerformanceInfo`: commit limit − физическая память, всего и занято | везде |
| Объём файла подкачки (всего) | `GetPerformanceInfo`: commit limit − физическая память | везде |

Медиа-счётчики `engtype_VideoEncode`/`engtype_VideoDecode` появляются только когда игра или
браузер реально нагружает движок, поэтому нулевые значения — это нормальный ответ, а не
отсутствие драйвера. Если для выбранного LUID ни одного инстанса нет, датчик пишет «нет данных».

`yawa-probe` печатает строку «Медиа-движки да/нет, PCI-e да/нет, файл подкачки да/нет»:
по ней видно, что поднялось на конкретной машине.

## Проверка на разном железе

Что проверяется и чем, без установки драйверов и SDK:

| Железо | Загрузка GPU | Медиа-движки | PCI-e | Температура GPU |
|---|---|---|---|---|
| NVIDIA (GeForce/RTX) | PDH GPU Engine | PDH + NVML | NVML | NVML |
| AMD (Radeon, iGPU 780M) | PDH GPU Engine | PDH GPU Engine | нет данных | ADL PMLog / Overdrive 5 при поддержке драйвером |
| Intel (Arc, Iris Xe) | PDH GPU Engine | PDH GPU Engine | нет данных | IGCL при поддержке драйвером |
| Любой x86/x64 CPU | `NtQuerySystemInformation` | — | — | PawnIO при поддержке CPU |

Общее для всех — загрузка GPU, видеопамять (DXGI), память, диск, сеть, кадры и файл подкачки:
эти источники встроены в Windows и не зависят от производителя. Приватные API (NVML, ADL,
IGCL) подключаются динамически и только для дополнительных показателей; их отсутствие не
ломает остальные датчики, а даёт «нет данных».

Проверка на конкретной машине: запустить `yawa-probe.exe` рядом с `YawaFpsHub.exe` и
посмотреть строки `GPU:`, `Медиа-движки`, `PCI-e`, `файл подкачки` и список адаптеров.

## Температуры, частоты, питание

| Источник | Что даёт | Лицензия / установка | Решение |
|---|---|---|---|
| NVML (`nvml.dll`) | температура, частоты, питание, вентилятор NVIDIA | ставится с драйвером, проприетарная, но бесплатная | берём, грузим динамически |
| ADL (`atiadlxx.dll`) | edge/hotspot, частоты, ASIC power, RPM при поддержке драйвером | MIT ABI-заголовки AMD, DLL в драйвере | реализовано; нужна проверка на GPU |
| IGCL | температура, частоты, энергия/мощность и RPM при поддержке драйвером | лицензия Intel на ABI-заголовок; DLL в драйвере | реализовано; нужна проверка на GPU |
| PawnIO (встроен) | MSR/SMN Intel 6, AMD Zen 17h/19h/1Ah | GPL-2.0-or-later с IOCTL-исключением, модули LGPL-2.1-or-later; автоподготовка с UAC | реализовано для поддерживаемых CPU, требуется проверка на Windows |
| [LibreHardwareMonitor](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor) | MSR и SMBus: температуры CPU, чипсета, NVMe | MPL-2.0, требует другого kernel-драйвера | не подключён |
| ACPI/PDH/WMI-термозоны | температура термозоны платы, не CPU | встроено | исключены из датчика CPU |

Температура CPU читается только из PawnIO на поддерживаемых CPU. Если аппаратный
источник недоступен, показано «нет данных», а не температура другой части системы.

### Резервный режим без доступа к kernel-датчикам

При обычном запуске на поддерживаемом CPU приложение само запрашивает UAC, если
недостаточно прав, затем проверяет и при необходимости устанавливает встроенный
подписанный PawnIO через SetupAPI. Скачивать или устанавливать его вручную не нужно.
Windows не разрешает обойти UAC: из-за ACL PawnIO SYSTEM/Administrators доступ к
аппаратным показателям может требовать подтверждения **при каждом запуске**.
Отказ UAC, несовместимый уже установленный пакет, блокировка драйвера политикой
Windows или неподдерживаемый CPU не мешают остальному мониторингу. Температура и
мощность CPU тогда остаются «нет данных», ACPI-термозона не подставляется.
Служба и устройство остаются в Windows после закрытия: один exe — один файл поставки,
а не отсутствие регистрации драйвера. Поведение UAC/SetupAPI пока не проверено на
реальном Windows-компьютере.

Питание CPU без драйвера уровня ядра прочитать нельзя: RAPL/MSR требуют kernel-драйвера,
поэтому «Питание» показывает значение только там, где его отдаёт встроенный источник, и
иначе пишет «нет данных». `yawa-probe` печатает список того, что реально поднялось на
конкретной машине.

Имя процессора для карточки «Процессор» берётся из
`HKLM\HARDWARE\DESCRIPTION\System\CentralProcessor\0\ProcessorNameString`, чистится от
`(R)`, `(TM)`, «CPU», «N-Core Processor» и «@ x.xxGHz» — остаётся «Ryzen 7 7800X3D».

## Монитор

Разрешение и герцовка основного экрана читаются через `EnumDisplaySettingsW(ENUM_CURRENT_SETTINGS)`,
имя — через `EnumDisplayDevicesW`. Они показываются в подзаголовке карточки «Кадры в секунду»,
на экране «Настройки» и служат целью кадра по умолчанию (`target_auto = 1`), чтобы бюджет кадра
считался от реальной герцовки, а не от константы 60 Гц.

## Паспорт машины и узкое место

Экраны «Сведения о системе» и «Баланс системы» не спрашивают ничего у производителя железа:
всё берётся из встроенных источников Windows,те же используются один раз при запуске.

| Данные | Источник | Если источник молчит |
|---|---|---|
| Модель и вендор CPU | `__cpuid` (листы 0x80000002…0x80000004), резерв — `ProcessorNameString` из реестра | имя остаётся пустым, индекс не выдумывается |
| Ядра, потоки, кэш L3, SMT | `GetLogicalProcessorInformationEx(RelationAll)` | число потоков из `GetActiveProcessorCount`, ядра не указываются |
| Базовая частота | `HKLM\HARDWARE\DESCRIPTION\System\CentralProcessor\0\~MHz` | «нет данных» |
| Модель Windows, версия функционала, сборка | `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion` — то же, что читает `winver` (`ProductName`, `DisplayVersion`, `CurrentBuildNumber`, `UBR`, `EditionID`); сборка ≥ 22000 отображается как Windows 11, потому что реестр по-прежнему пишет «Windows 10» | пустые строки |
| Список видеокарт, вендор, объём памяти | DXGI (`EnumAdapters1`), общий реестр `GpuRegistry` | список пуст |
| Версия драйвера видеокарты | `MatchingDeviceId` + `DriverVersion` из `HKLM\SYSTEM\CurrentControlSet\Control\Class\{4d36e968-…}` по PCI-идентичности адаптера | строка «нет данных» |
| Модули памяти: слот, объём, тип, паспортная и настроенная частота, вендор, партномер, напряжение | SMBIOS Type 16/17 через `GetSystemFirmwareTable('RSMB')`; при неполных полях — `Win32_PhysicalMemory`, количество слотов — `Win32_PhysicalMemoryArray.MemoryDevices` из WMI | если и WMI молчит, только полный объём из `GlobalMemoryStatusEx`; неизвестную настроенную частоту не заменяем паспортной |
| Мониторы: имя, разрешение, герцовка, масштаб | `EnumDisplayDevicesW` + `EnumDisplaySettingsExW(ENUM_CURRENT_SETTINGS)`, `GetDpiForSystem` | пустой список |

**Тайминги ОЗУ.** SPD содержит паспортные профили, а действующие
`tCL-tRCD-tRP-tRAS` требуют чтения контроллера памяти с учётом его модели.
Экспериментальный источник ограничен AMD Family 17h model 71h (Matisse) и
Family 19h model 50h (Cezanne, в том числе Ryzen 7 5800H) с DDR4: PawnIO однократно
читает UMC в двух каналах, проверяет код типа памяти и наличие модуля, отбрасывает
сбойные и несогласованные результаты. Для других моделей, отказа доступа,
неоднозначных регистров и неподтверждённого типа памяти остаётся «недоступны».
Раскладка `0x50204`/`0x50208` сверена с публичной таблицей
[ZenStates-Core](https://github.com/irusanov/ZenStates-Core/blob/869b7e82572337e5a673e92230edc92bddf0e44b/Dictionaries/DDR4Dictionary.cs)
(использованы адреса и поля, не код проекта); идентичность Cezanne model 50h
сверена с [таблицей моделей](https://github.com/irusanov/ZenStates-Core/blob/869b7e82572337e5a673e92230edc92bddf0e44b/Cpu.cs).
Тесты используют **искусственные** слова UMC: новые показания на 5800H и разных BIOS
ещё не проверены, поэтому регистры и результаты нельзя считать подтверждёнными.
SPD/XMP/EXPO этот источник не читает. Только по явному запуску
`YawaFpsHub.exe --probe --dump=memory` основной exe выводит в stdout сырые
регистры конфигурации и таймингов **только этих моделей**; другой информации о
модулях не собирает и ничего не отправляет. Вывод конфигурации памяти может быть
чувствителен — см. [инструкцию](../README.md#добровольный-дамп-памяти).
В карточке памяти показываются данные SMBIOS и, при неполных полях, WMI: тип,
паспортная и настроенная скорости и доступное напряжение. Расчётный период
`tCK = 2000 / MT/с` оставлен только в `yawa-probe` с пометкой «не замер»;
это не действующий тайминг контроллера.
Смещения Type 16/17 сверены с DMTF/dmidecode: число устройств `0x0D`, размер `0x0C`,
тип `0x12`, скорость `0x15`, настроенная скорость `0x20`; разбор проверяется тестом
с двумя модулями. Если у модулей разная либо неизвестная настроенная скорость, общее
значение остаётся неизвестным.

**Офлайн-декодер SPD (первый шаг).** `app/metrics/spd.h` разбирает только
CRC-проверенные первые 128 байт DDR4/DDR5: тип и минимальный паспортный период
`tCK`; для DDR4 — расчётную ёмкость модуля и базовые JEDEC tAA/tRCD/tRP/tRAS.
Для DDR5 размер и тайминги остаются неизвестными: они требуют проверенных следующих
страниц, которых декодер пока не использует. XMP/EXPO, производитель и партномер
не декодируются. Фрагменты SPD-образов в `tests/test_spd.cpp` взяты из
[coreboot DDR4](https://github.com/coreboot/coreboot/blob/1879b6a34a6e93a93d691a0d9f2457d6251a17c1/src/mainboard/google/hatch/spd/8G_2666.spd.hex)
и [coreboot DDR5](https://github.com/coreboot/coreboot/blob/1879b6a34a6e93a93d691a0d9f2457d6251a17c1/src/mainboard/intel/adlrvp/spd/adlrvp_ddr5_mr.spd.hex),
по 128 байт с подтверждённым CRC (blob SHA-1 в тесте). Это публичные образы
прошивки, **не** дампы с машин пользователей и не проверка аппаратного чтения.
В exe и UI декодер ещё не подключён; SMBus-модули не добавлены, доступа к SPD нет.
Паспортный минимум не подменяет действующую частоту или состояние XMP/EXPO.

WMI обычно получает сведения от той же прошивки; это не независимый датчик частоты и
не измерение действующих таймингов. Датчики и сведения о железе инициализируются после
показа окна: быстрый паспорт CPU/SMBIOS/DXGI публикуется первым, WMI дополняет его позже.
Если WMI задерживается, интерфейс работает с уже полученными данными. При
закрытии приложение ждёт завершения опросов; если драйвер навсегда задержал отменённый
запрос, через 15 секунд запускается аварийное завершение **собственного** процесса.

### Как считается узкое место

На экране разделены загрузка игры и загрузка всей системы. Для вердикта нужна активная
игра с кадрами ETW: CPU — разница времени ядра/пользователя процесса по PID,
нормированная на число логических процессоров, и отдельно самый занятой поток **этого PID**
(ёмкость одного ядра); GPU — PDH `GPU Engine` для того же PID, выбранного LUID и
`engtype_3D`. Вердикт использует загрузку игры, не общесистемные счётчики. При обеих нагрузках ниже 75 %,
недоступном счётчике или отсутствии игры вывод не делается: ограничение кадров,
ожидание ввода/диска и особенности движка способны исказить простой одного узла.
Герцовка экрана и нагрузка посторонних процессов в вердикте не участвуют.

Индексы паспортной производительности CPU/GPU есть во внутренней модели для справочной
карточки «Связка», но не подменяют замеры игры на экране. Процент по отношению нагрузок
— эвристика, а не измеренный прогноз прироста FPS после апгрейда.

Рекомендации генерируются от вывода, а не печатаются списком подряд: при упоре в процессор
это перенос нагрузки на GPU (повысить разрешение или DSR/VSR), настройки, снижающие нагрузку на CPU,
лимит кадра и проверка однопоточности; при упоре в видеокарту — апскейлер, тяжёлые для GPU
эффекты, нехватка видеопамяти и лимит питания. Отдельные пункты включаются только если
условие видно по данным: ОЗУ занято больше 90 %. XMP/EXPO и режим каналов
из SMBIOS не определяются и не используются в рекомендациях.

### Что видно на разном железе

| Платформа | Паспорт и индекс | Живое узкое место |
|---|---|---|
| NVIDIA (GeForce) | имя из DXGI, драйвер из реестра, температуры/питание из NVML | загрузка CPU и GPU есть → расчёт по замерам |
| AMD (Radeon) | имя и объём из DXGI, версия драйвера из реестра; NVML нет | PDH-движки → расчёт по замерам; питание и температуры — ADL при поддержке |
| Intel (Arc, Iris, UHD) | имя и объём из DXGI, драйвер из реестра | то же; для iGPU индекс получается низким, поэтому прогноз честно говорит об упоре в GPU |
| Без дискретной карты | встроенный адаптер становится «основным» | прогноз по индексу, рекомендации по разрешению не показываются |
| Виртуалка / Basic Render Driver | CPU и память определяются, GPU — «нет данных» | экран «Баланс» показывает «Недостаточно данных» |

## Остальное

- **PDH** `\Processor Information(_Total)\% Processor Performance` × номинальная частота из
  `HKLM\HARDWARE\...\~MHz` — текущая частота CPU.
- **`CallNtPowerInformation(ProcessorInformation)`** из `powrprof.dll` — резервный источник
  частоты: работает без счётчиков PDH и без драйверов. Если молчит и он, показывается
  номинал из реестра, чтобы строка не оставалась пустой.
- **PDH** `\PhysicalDisk(_Total)\Disk Read Bytes/sec` и `\Network Interface(*)\Bytes Received/sec` —
  уже готовые скорости; повторно брать дельту нельзя, иначе значения уезжают в миллиарды
  (эта ошибка была поймана прогоном `yawa-probe` в CI).
- **`GetSystemTimes`**, `GlobalMemoryStatusEx`, `GetPerformanceInfo` — загрузка CPU, память, кэш, своп.
- **`NtQuerySystemInformation(SystemProcessorPerformanceInformation)`** — загрузка по ядрам:
  время простоя и полное время каждого логического процессора, проценты считаются по дельте
  между опросами, как в диспетчере задач. PDH-счётчики `\Processor Information(0,N)\...` здесь
  не используются: на части машин экземпляры не открываются, и датчики оставались пустыми.
- **`GetForegroundWindow`**, `GetWindowThreadProcessId`, `OpenThread`, `GetThreadTimes` + QPC —
  «Поток игры»: загрузка главного потока активной игры. Без запущенной игры датчик честно
  показывает «нет данных», а не ноль.
- **`GetProcessTimes`**, `GetProcessMemoryInfo` — собственное потребление приложения.

Имена счётчиков запрашиваются через `PdhAddEnglishCounterW`: на русской Windows локализованные
имена обычный `PdhAddCounter` не находит.

## Интеграция PawnIO: первый этап

- `PawnioSensors` открывает `GLOBALROOT\Device\PawnIO`, проверяет ABI/версию,
  загружает официальный подписанный CPU-модуль из RCDATA. DLL PawnIOLib не используется.
  Чтение ограничено зашитыми в C++ адресами, пользовательских IOCTL/адресов нет.
- Intel family 6: package thermal status / temperature target и RAPL package energy.
  Отсутствующий MSR или невалидный DTS не заменяется оценкой. Проверяется CPUID package DTS.
- AMD family 17h/19h/1Ah: Tctl `THM_TCON_CUR_TMP` через SMN и package energy MSR.
  Доступ к SMN защищён общим `Global\Access_PCI`; при таймауте/ошибке блокировки
  измерение пропускается. Общий регистр Zen/Tctl подтверждён также для 1Ah; CCD отдельно не читаются.
- Чтение привязано к CPU 0 группы 0; affinity восстанавливается. Многосокетная
  агрегация не реализована. ACPI-резерв не используется.
- Мощность считается по дельте 32-битного счётчика энергии с учётом energy unit,
  времени и одного переполнения. Первый отсчёт, разрыв более 10 секунд, изменение
  единиц, ошибка чтения и неправдоподобный скачок не выдаются за измерение.
- При обычном запуске на поддерживаемом CPU — проверка прав и автоматический запуск
  этого же exe через системный UAC. Если установка нужна, окно подтверждения
  с отменой по умолчанию; служебная команда `--install-sensors` остаётся для диагностики,
  пользователю она не требуется. SHA-256 SYS/INF/CAT закреплены; каталог
  распаковки в Program Files имеет ACL Administrators/SYSTEM. Проверяется Authenticode
  через WinVerifyTrust по дополнительной подписи Microsoft (индекс 1), без сетевых
  обращений; пакет принимает/отклоняет Windows SetupAPI.
  Существующие устройства не удаляются при ошибке; откатывается лишь созданное нами.
- В exe входят неизменённые SYS/INF/CAT, два `.bin` и `sources.zip` с исходниками
  upstream-тегов, submodule PawnPP и лицензиями. Исходники экспортируются командой
  `--sensor-sources`. Подмена любого payload блокирует конфигурацию CMake по SHA-256.

Это реализация клиента/упаковки, не подтверждение работы на всех CPU. Windows runtime,
установка/откат, kernel-policy, каталог CAT, Secure Boot/HVCI и показания реального
железа ещё не проверены. UI не менялся: показания идут через существующий SystemSnapshot
в датчики, запись и оверлей. Управление вентиляторами, напряжениями и разгоном не добавлено.


## Расширение GPU и накопителей

`VendorGpuSensors` использует неизменённые официальные ABI-заголовки ADL и IGCL
(происхождение и лицензии в `third_party/gpu_sdk/README.md`). Динамически загружаются
только системные DLL установленного GPU-драйвера. Контекст Intel создаётся только
при наличии Intel-адаптера; запрашиваются исключительно read/telemetry функции.
Тип, units и supported проверяются до преобразования чисел. При ошибке данные
очищаются, а накопительная мощность заново набирает базу. Не обещается поддержка
температуры/энергии на каждом Intel iGPU или старом AMD.

Привязка: Intel — LUID, AMD — display source/LUID либо однозначный единственный
AMD-адаптер с совпадающим именем. Клоны ADL одного BDF не считаются разными GPU.
NVML не имеет использованного здесь LUID API: при двух одинаковых именах датчики
отключаются вместо выбора индекса 0. Неверная сигнатура RPM NVML исправлена:
`nvmlDeviceGetFanSpeedRPM` получает version/fan/speed структуру, а не `unsigned*`.
Проценты вентилятора не переводятся в выдуманные RPM. NVML temperature/clock/power
экспорты теперь необязательные: отсутствие одного не отключает все остальные.

`StorageSensors` перечисляет disk interfaces через SetupAPI, опрашивает Windows
StorageDeviceTemperatureProperty и NVMe Health Log (page 2). Температура NVMe —
16-битный little-endian Kelvin; проверяются размер, offset, длина и sentinel.
UI получает максимум температур доступных дисков. Запросы идут в отдельном потоке,
период 5 секунд, freshness 15 секунд. Overlapped IO имеет таймаут и CancelIoEx;
освобождение буфера ждёт подтверждения завершения/отмены ядром. Неисправный драйвер,
который не завершает отмену, всё ещё может задержать остановку — это не обещание
жёсткого realtime. Не реализованы проприетарные USB/RAID/NVMe passthrough и все ATA SMART.

AMD 1Ah включён после сверки общего регистра Zen `0x59800`, полей диапазона и
разрешения семьи официальным модулем 0.2.11. Дополнительная проверка аппаратных
полей: https://github.com/torvalds/linux/blob/master/drivers/hwmon/k10temp.c .
Код Linux не переносился; отдельные CCD, модельные Tdie-offset и калибровки не добавлены.
Температура по-прежнему Tctl, не универсальная Tdie.

Реальные API-ответы NVIDIA/AMD/Intel, SMART разных контроллеров, запуск/установка
kernel-пакета и работа одновременно с другими мониторами остаются аппаратной
матрицей для Windows. Наличие реализации и успешная сборка не подтверждают эту матрицу.
