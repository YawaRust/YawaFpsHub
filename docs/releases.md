# Выпуск

## Что уходит в релиз

Ровно один файл — `YawaFpsHub.exe`. Ни архивов, ни `ini`, ни `yawa-probe`, ни PDB:
проверка `github-workflow` считает ассеты и падает, если их больше одного. exe линкуется со
статическим CRT, поэтому Visual C++ Redistributable на машине пользователя не нужен; все
остальные импорты — системные DLL из `System32`, их список проверяется на сборке.

## Номер версии

Единственный источник — файл `VERSION` в корне. Из него CMake берёт `PROJECT_VERSION`,
в свойства exe (`app/resources/resource.rc.in`) и в рельс интерфейса попадает та же строка.

Правила подъёма:

| Было | Стало |
|---|---|
| `1.0.0` | `1.0.1` |
| `1.0.8` | `1.0.9` |
| `1.0.9` | `1.1.0` |
| `1.9.9` | `2.0.0` |

Патч и минор не бывают больше 9: следующий шаг переносится в старший разряд.
Автоматические теги сборок имеют вид `v<версия>-build.<номер запуска Actions>`.
Ручной workflow `release` по-прежнему создаёт тег `v<версия>` и сверяет его с `VERSION`.

## Команды

```bash
python3 tools/version.py show                 # текущая версия
python3 tools/version.py bump --kind patch    # next → 1.0.1
python3 tools/version.py bump --kind patch --write   # то же, но записывает VERSION
python3 tools/version.py notes 1.0.1          # тело релиза из CHANGELOG
```

## Как опубликовать

После каждого успешного push в `main` workflow `build` дожидается тестов Linux/Windows,
сборки exe и диагностики на Windows. Затем отдельный job скачивает **тот же** exe
из артефакта сборки и создаёт Release с одним файлом. Неуспешные сборки, проверки PR
и сборки `arena/**` релизы не публикуют. Повтор запуска обновляет тот же тег,
номер версии в `VERSION` автоматически не повышается.

Для отдельного номерного релиза с заметками из `CHANGELOG.md` доступен ручной запуск
workflow `release` на `main` с `bump: patch` или `minor`. Он самостоятельно поднимет
версию, соберёт и опубликует `v<версия>` после тестов; это отдельный путь выпуска,
не обязательный для автоматических сборок.
