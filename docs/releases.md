# Выпуск

## Что уходит в релиз

Ровно один файл — `YawaFpsHub.exe`. Ни архивов, ни `ini`, ни `yawa-probe`, ни PDB:
проверка `github-workflow` считает ассеты и падает, если их больше одного. exe линкуется со
статическим CRT, поэтому Visual C++ Redistributable на машине пользователя не нужен; все
остальные импорты — системные DLL из `System32`, их список проверяется на сборке.

## Номер версии

Единственный источник — файл `VERSION` в корне. Из него CMake берёт `PROJECT_VERSION`,
в свойства exe (`app/resources/resource.rc.in`) и в рельс интерфейса попадает та же строка.

Правила подъёма:

| Было | Стало |
|---|---|
| `1.0.0` | `1.0.1` |
| `1.0.8` | `1.0.9` |
| `1.0.9` | `1.1.0` |
| `1.9.9` | `2.0.0` |

Патч и минор не бывают больше 9: следующий шаг переносится в старший разряд. Тег всегда
`v<версия>`, и workflow сверяет тег с `VERSION` — релиз с разошедшимися номерами не соберётся.

## Команды

```bash
python3 tools/version.py show                 # текущая версия
python3 tools/version.py bump --kind patch    # next → 1.0.1
python3 tools/version.py bump --kind patch --write   # то же, но записывает VERSION
python3 tools/version.py notes 1.0.1          # тело релиза из CHANGELOG
```

## Как опубликовать

1. Записать раздел новой версии в `CHANGELOG.md` (заголовки вида `## 1.0.1 — 12 ноября 2026`,
   секции «Новое / Улучшено / Исправлено», только то, что видно пользователю).
2. Поднять `VERSION` тем же `tools/version.py bump --write` и закоммитить.
3. `git tag v1.0.1 && git push origin v1.0.1` — workflow `release` соберёт exe, проверит
   самодостаточность и создаст релиз с телом из `CHANGELOG.md`.

Тот же workflow можно запустить вручную (`workflow_dispatch`) с `bump: patch` — тогда он
сам поднимет версию, закоммитит `VERSION` в ветку, соберёт и опубликует релиз. С `bump: none`
будет собран и выложен релиз текущей версии из `VERSION`.
