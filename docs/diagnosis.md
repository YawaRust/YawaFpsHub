# Диагностические находки: первый офлайн-срез

`app/metrics/diagnosis.{h,cpp}` — портируемое ядро без сети и без доступа к игре.
Поток опроса Win32 передаёт ему FPS и PID активного потока кадров, CPU и самый занятый
поток этого PID, а также 3D-счётчик GPU, отфильтрованный по PID и LUID выбранной
карты. Только при наличии согласованных свежих данных первая находка показывается
на экране «Баланс» в карточке предпросмотра. Если данных нет, карточка так и пишет;
старая находка сбрасывается при паузе, перезапуске ETW и смене активного процесса.
`capture_failed` пока не выводится в приложении: остановленная ETW-сессия и отсутствие
кадров не доказывают подтверждённый сбой для PID. Макет `ui-prototype/` отдельно
демонстрирует условный пример и маркирует вымышленные числа.

`GameDiagnosisInput` принимает ненулевой PID активной игры, свежий замер (не старше
2 с), подтверждённое состояние сбора кадров и кадры именно этой игры. Проценты CPU
и самого занятого потока должны относиться к PID игры; GPU 3D берётся только
из счётчика этого PID на выбранном LUID (`gpuMatchesGame`), а не из общей загрузки
адаптера. Это эвристика, а не доказательство причины просадки. Отсутствие данных,
несовпадение LUID и устаревший замер не заменяются средними по системе или
паспортным прогнозом.

| Код | Достоверные входы | Вывод |
|---|---|---|
| `gpu_bound` | кадры игры > 0, GPU 3D процесса ≥ 95 %, CPU процесса ≤ 70 %; если известна загрузка потока игры, она < 90 % | возможный упор в GPU, confidence 75 |
| `cpu_bound` | кадры игры > 0, поток игры ≥ 90 %, GPU 3D процесса ≤ 85 % | возможный упор в CPU, confidence 75 |
| `capture_failed` | явное подтверждение сбоя захвата для PID | сбой захвата, confidence 95 |

Если и GPU, и поток игры нагружены до порога, единственный виновник не назначается.
Порог упора не зависит от герцовки дисплея. Отсутствие кадра **само по себе**
не означает сбой ETW; нужен подтверждённый статус. `fps_capped_60`, VRAM overflow,
троттлинг, XMP и остальные правила §7.3.4 пока не реализованы: для них нужны
достоверные сигналы, которых этот вход не предоставляет.

Первый офлайн-срез формата `.yawa` — `app/report/package.{h,cpp}`: ZIP без сжатия,
`manifest.json` со `schema: 1`, `system.json`, `session.json`, `sensors.csv`,
`audit.json`, `diagnosis.json`, `screen.png`. Он принимает только уже показанную
пользователю PNG-карточку (не более 32 МиБ, с проверкой структуры и CRC PNG),
свежие показатели PID/LUID и находки ядра. Имя пользователя, пути, имена процессов,
сырые журналы и скрытые индивидуальные настройки не добавляются. `system` и `audit`
пока помечены `not_collected`, `session` — `instantaneous_only` или `no_game_sample`;
синтетических 60 секунд нет. Флаг `game_frame` — `omitted`, пока пользователь
отдельно не включил кадр и не увидел итоговую карточку. Чтение `schema: 1` принимает
только семь известных несжатых ZIP-записей с ограничениями размеров и CRC, валидную
структуру PNG с лимитом 16 млн пикселей и корректный JSON в четырёх файлах данных
(UTF-8 и вложенность до 16 уровней). В `schema: 1` допустим только пустой
`sensors.csv` с заголовком: записи датчиков ещё не создаются и не принимаются.
`system`/`audit` содержат только `status: not_collected`; `session` принимает только
`no_game_sample` без полей или `instantaneous_only` с возрастом ≤ 2000 мс,
опциональным FPS (0–100000) и процентами (0–100). Неизвестные и повторяющиеся поля
отклоняются. Семантика полей `diagnosis.json`, содержимое пикселей PNG и
соответствие карточки данным **пока не проверяются**: будущему просмотрщику
нельзя считать данные доверенными. Ни чтение, ни сериализация не открывают пути
на диске.
Кнопка на экране «Баланс» создаёт отдельную карточку 1920×1080 через Direct2D/WIC:
модальный предпросмотр показывает те же пиксели, что запишутся в PNG или в
`screen.png` пакета `.yawa`. Кадр игры по умолчанию отсутствует, в файл попадают
лишь достоверные показатели активного PID/LUID. Без игры виден статус «нет данных».
Экспорт запускается только явным нажатием «Сохранить» в этом окне. По отдельной
кнопке «Кадр через 5 с» предпросмотр скрывается: пользователь переключается в
окно игры, замеченное не более 30 секунд назад. Перед захватом сверяется то же
окно, затем `captureForegroundGameClient` проверяет её PID, монитор и клиентскую
область и получает кадр Desktop Duplication без инъекции или записи
файла. После захвата предпросмотр возвращается; мышью можно закрыть до 16
прямоугольников непрозрачными масками или полностью убрать кадр. Сохраняемые PNG
и `screen.png` пакета совпадают с показанной после масок карточкой; флаг
`game_frame: included` выставляется только при наличии кадра. Другие окна,
уведомления и оверлеи могут оказаться поверх игры — перед сохранением их нужно
проверить и закрыть. При сбое кадр не сохраняется, исходные пиксели не пишутся
отдельным файлом. HDR-панель пока отклоняется без тонмаппинга; аппаратная и
UX-проверка нового пути ещё не выполнена.
Ограниченная CLI-команда `--report=<путь-к-файлу.yawa>` читает локальный файл не
более 33 МиБ, валидирует `schema: 1` указанным выше reader и выводит только
статус пакета, наличие кадра и JSON сессии. Не открывает PNG, не извлекает
содержимое на диск, не загружает драйвер и отказывает сетевым UNC-путям.
GUI-просмотр пакета, `--capture`, кадрирование и аудит ещё не готовы. `PrintWindow` как резерв для эксклюзивного полноэкранного режима
не подключён: синхронный вызов может заблокировать UI зависшего окна. Браузерный макет позволяет
добровольно выбрать **локальную** картинку, кадрировать её ползунками, закрыть
прямоугольники и скачать только помеченную как демонстрационную PNG-карточку
1920 px. Он не доказывает принадлежность картинки игре и не сохраняет `.yawa`.
Windows- и визуальная UX-проверка не проводились.
